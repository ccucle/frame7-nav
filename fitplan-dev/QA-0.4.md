## HTTP 통합 검증

Node의 실제 HTTP 서버에 `FormdayCloud` 클라이언트를 연결했다. 외부 서비스가 아니라 loopback 서버와 테스트용 쿠키 저장기, 명시적으로 주입한 메모리 저장 어댑터를 사용했다.

1. 가입 → 사용할 기록 명시 선택 → 기존 비로그인 기록 업로드 → 별도 기기 로그인과 서버 기록 받기 → 각 기기 편집 → 409 충돌 → 사용자 선택 → 204 로그아웃.
2. 서버는 저장했으나 성공 응답만 유실된 상황을 재현했다. 클라이언트 재시작 후 같은 작업 번호와 내용으로 재시도하며, 이후의 새 편집도 보존했다.
3. 복구 코드로 비밀번호를 바꾼 뒤 이전 세션이 폐기되고, 기존 기기의 미전송 편집은 같은 계정 재로그인 후 전송되었다.
4. 세션 만료와 다른 탭의 계정 변경에서 예상 사용자 ID를 확인하여 다른 계정의 데이터를 캐시에 넣지 않았다.
5. PostgreSQL JSONB처럼 응답의 객체 키 순서를 바꾸어도 의미가 같은 저장 결과는 정상 확인했다.
6. 기록 선택 전에 세션이 만료된 경우 표시된 재로그인 기능이 실제로 동작하고, 재로그인 뒤에도 사용할 기록을 직접 선택해야 했다.

이 HTTP 테스트는 쿠키 속성의 응답 문자열을 확인하지만 브라우저의 Secure 쿠키 정책을 구현하거나 증명하지 않는다. 실제 HTTPS/Render 프록시 확인은 별도다.

## SQL 검증과 한계

테스트 전용 `@electric-sql/pglite 0.5.17`의 PostgreSQL WASM 엔진에서 운영용 SQL 어댑터와 마이그레이션을 실행했다.

- DDL, JSONB, 사용자 이름 고유 제약, 외래 키, 삭제 cascade를 확인했다.
- 세션 생성에 실패하면 새 사용자와 문서가 함께 롤백되는지 확인했다.
- 문서와 재시도 응답이 한 트랜잭션에서 함께 저장되거나 함께 롤백되는지 확인했다.
- 사용자가 다르면 문서에 접근하지 못하고, 이전 버전 저장은 충돌로 거부되는지 확인했다.
- 복구 코드 재사용을 막고, 이전 인증 세대에서 검증한 로그인으로 새 세션을 만들지 못하는지 확인했다.
- DB에 보관된 요청 빈도 제한과 작업 응답 32개 보관 한도를 확인했다.
- 디스크에 저장한 뒤 엔진을 닫고 다시 열어 문서가 유지되는지 확인했다.

PGlite 테스트는 단일 연결을 사용하므로 실제 PostgreSQL 다중 연결의 행 잠금 실행 순서, `pg` TCP 인증, Render TLS, 배포 마이그레이션을 검증한 것은 아니다. 이 항목은 인프라 승인 후 실제 배포에서 확인한다.

## 독립 리뷰에서 수정한 항목

- 만료된 세션의 동일 계정 재로그인이 기록 선택 전에는 거부되는 조건을 수정했다.
- 일정 수가 0이어도 저장된 내 식품·즐겨찾기·목표가 삭제될 수 있으므로, 기기 기록으로 계정을 갱신할 때 항상 전체 교체 확인을 받게 했다.
- 화면 개수를 일정 수로 명시했다. 알 수 없는 수를 0개로 표시하지 않는다.
- JSONB 객체 키 순서를 기록의 차이로 오인하던 비교를 수정했다.
- 복구 코드를 보관하기 전에 창을 닫을 때 코드가 다시 표시되지 않는다는 구체적인 확인 문구를 추가했다.
- 로그인 선택 대기 중인 미전송 계정 캐시의 내보내기가 비로그인 기록을 잘못 내보내지 않는지 확인했다.

## 운영 배포와 브라우저 확인 상태

운영 주소는 계속 **v0.3.0**이다. 이 단계에서 새 웹 서버·PostgreSQL·유료 저장 공간을 생성하지 않았고, v0.4 로그인 기능을 운영 사이트에 게시하지 않았다.

v0.3 식단 기능의 실제 Chrome 확인 결과는 [QA-0.3.md](QA-0.3.md)에 있다. v0.4 계정 UI의 실제 브라우저 렌더링과 iPhone/Safari 확인은 아직 수행하지 않았다. DOM 어댑터 테스트는 실기기 화면 검증을 대신하지 않는다.

비용, 실제 쿠키 왕복·캐시 격리·두 기기 확인 절차는 [ACCOUNTS-ROLLOUT.md](ACCOUNTS-ROLLOUT.md)에 정리했다.
