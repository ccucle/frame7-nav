# FORMDAY 계정 저장 활성화 계획

작성일: 2026-11-23 (Asia/Seoul)  
후보 버전: `v0.4.0-rc.1`  
작업 브랜치: `fitplan-accounts-20261123`

## 현재 상태

운영 사이트는 `v0.3.0`이며 브라우저 저장 방식으로 동작한다. 이 후보 브랜치에는 계정 화면, 동기화 모듈, 인증 API, PostgreSQL 스키마와 저장 어댑터가 들어 있다. 새로운 유료 서비스나 DB는 아직 만들지 않았다. 운영 사이트에서 로그인과 기기 간 동기화가 이미 활성화된 것은 아니다.

- 운영 주소: https://formday-fitplan-ccucle.onrender.com/?v=0.3.0
- 운영 소스 브랜치: `fitplan-site-20261123`
- 기존 정적 서비스: `formday-fitplan-ccucle`
- 기존 서비스의 자동 배포는 꺼져 있다.
- 활성화 전 실제 Render DB 연결, HTTPS 쿠키 왕복, 프록시의 캐시 동작과 두 브라우저 검증이 남아 있다.

## 구현한 사용자 흐름

1. 아이디·비밀번호로 계정을 만든다. 아이디는 4~32자 영문·숫자·`._-`이며 소문자로 저장한다. 비밀번호는 15~128자다.
2. 가입 직후 복구 코드를 한 번 표시한다. 별도로 보관했는지 확인한 뒤 기록 선택으로 이동한다. 코드와 비밀번호를 모두 잃으면 이메일로 복구할 수 없다.
3. 처음 연결할 때 **계정 기록 사용** 또는 **이 기기 기록을 계정으로 옮기기**를 직접 선택한다. 로그인만으로 기존 브라우저 기록을 업로드하지 않는다.
4. 계정을 사용 중일 때 변경 사항은 먼저 그 계정의 기기 저장소에 보관하고, 약 700ms 뒤 서버 저장을 시도한다. 실패한 전송 내용과 작업 번호는 보존한다.
5. 다른 기기의 변경은 계정 메뉴의 **지금 동기화**로 조회한다. 초기 연결 때도 서버를 조회한다. 실시간 구독, 주기 조회, 네트워크 복구 시 자동 재시도는 이번 버전에 없다.
6. 양쪽에서 변경한 경우 자동 저장을 중지한다. 필요한 기록을 먼저 내보내고 사용할 쪽을 선택한다. 전체 문서를 교체하는 방식이며 개별 일정 자동 병합은 하지 않는다.
7. 미전송 변경을 동기화하거나 충돌을 해결한 뒤 로그아웃한다. 로그아웃은 해당 계정의 이 기기 캐시를 지우고 원래의 비로그인 기록으로 돌아간다.

동기화 문서는 일정·날짜별 운동 기록·식사·체중·내 식품·즐겨찾기·영양 목표를 포함한다. 화면의 개수는 기본 일정 개수이며 식품/즐겨찾기 개수나 반복 일정의 모든 발생 횟수를 뜻하지 않는다. 달력 화면 구성과 v3 백업 형식은 그대로 사용한다.

이메일 인증, Google 로그인, Google Calendar 연결, AI API는 포함하지 않는다. 비밀번호 변경과 계정 삭제 API는 서버에 준비되어 있지만 이 후보의 사용자 화면에는 아직 연결하지 않았다.

## 데이터 보존과 계정 경계

- 기존 비로그인 저장 키 `formday_calendar_proto_v1`와 직전 원본 백업은 보존한다.
- 계정 캐시는 사용자 ID를 포함한 별도 키에 저장한다. 다른 계정의 캐시와 공유하지 않는다.
- 백업 파일은 실제 선택 대상의 데이터로 만든다. 재로그인 대기 중에도 미전송 계정 캐시를 내보낸다.
- 서버 요청에는 인증 쿠키 외에 예상 사용자 ID를 넣는다. 쿠키가 다른 탭에서 다른 계정으로 바뀌면 서버와 클라이언트 양쪽에서 요청을 멈춘다.
- 서버 버전과 작업 번호를 함께 사용한다. 같은 요청의 응답을 잃으면 동일한 내용과 번호로 재시도하며 중복 저장을 방지한다.
- 전송 중 새 편집이 생기면 이전 응답으로 새 편집을 지우지 않는다.
- 기록 전환과 캐시 저장이 중간에 실패하면 원본과 대기 정보를 보존한다. `localStorage` 자체가 원자적 트랜잭션을 제공하는 것은 아니다.
- 세션이 만료되면 같은 계정으로 다시 로그인하도록 안내한다. 계정 선택 전 만료된 경우도 다시 로그인할 수 있다.
- 열어 둔 화면에서는 서버 연결이 끊겨도 기기에 기록할 수 있다. 오프라인에서 새로 열기, 캐시 삭제 이후 복원, 완전한 오프라인 앱 동작을 보장하는 PWA는 아니다.

## 인증과 서버 저장

운영 진입점 `fitplan-server/server.cjs`는 실제 PostgreSQL 연결과 스키마 확인에 실패하면 시작하지 않는다. 메모리 저장 어댑터는 테스트에서 명시적으로 주입할 때만 사용한다.

- 비밀번호: 고유 salt를 사용한 scrypt, `N=131072, r=8, p=1`. 동시에 하나의 계산과 최대 네 개의 대기 요청으로 메모리 사용을 제한한다.
- 세션: 256비트 난수, 유효기간 7일. 서버에는 토큰 해시만 저장하고 쿠키는 `Secure`, `HttpOnly`, `SameSite=Lax`, `__Host-` 범위를 사용한다.
- CSRF: 정확한 `Origin`, JSON 요청, 세션에서 파생한 CSRF 토큰을 확인한다. CSRF 토큰은 화면 실행 메모리에만 둔다.
- 복구 코드: 256비트 난수의 해시만 저장한다. 복구 시 새 코드로 교체하고 기존 세션을 모두 취소한다.
- 저장: 사용자 행 잠금, 인증 세대와 세션 재확인, 문서 버전 조건부 갱신을 하나의 트랜잭션에서 실행한다.
- 오류 응답·로그에 비밀번호, 세션, 복구 코드, DB URL, 사용자 문서를 기록하지 않는다.
- 재시도 응답은 사용자별 최근 32개를 유지하고 오래된 항목은 7일 기준 정리한다. 보존 범위를 벗어난 요청을 과거 버전으로 재전송하면 충돌로 중지한다.
- 요청 크기: 인증 16KiB, 기록 문서 16MiB. 별도로 구조 깊이·항목 수·API 요청 빈도를 제한하고, 큰 기록 요청은 한 번에 하나씩 처리하며 대기열은 최대 네 개다.
- 계정 문서는 PostgreSQL JSONB에 저장한다. 객체 키 순서가 바뀌어도 의미가 같은 응답을 정상 처리한다.

## 승인 후 적용할 설정

### 1. 저장소와 계정 서비스

DB와 웹 서버를 기존 사용자 작업 공간의 같은 Singapore 리전에 만든다. PostgreSQL 외부 접근은 필요하지 않으므로 비활성화하고 내부 연결 URL을 사용한다. DB 비밀번호와 URL은 서비스의 비밀 환경 변수로만 넣는다.

새 웹 서비스의 제안 이름은 `formday-accounts-ccucle`이다. 실제 공개 주소는 생성 결과를 확인한 뒤 사용하며 미리 존재하는 주소처럼 안내하지 않는다.

| 설정 | 값 |
| --- | --- |
| 저장소 | `ccucle/frame7-nav` |
| 최초 검증 브랜치 | `fitplan-accounts-20261123`의 검증한 커밋 |
| 루트 디렉터리 | 저장소 전체; `fitplan-server`로 좁히지 않음 |
| 빌드 명령 | `npm ci --omit=dev --prefix fitplan-server` |
| 배포 전 명령 | `npm run migrate --prefix fitplan-server` |
| 시작 명령 | `npm start --prefix fitplan-server` |
| 상태 검사 | `/readyz` |
| 자동 배포 | 끔 |
| `NODE_ENV` | `production` |
| `NODE_VERSION` | `24.22.3` (이번 검증 버전) |
| `DATABASE_URL` | 같은 리전 DB의 내부 URL, 비밀 값 |
| `DATABASE_TLS` | `render-internal` |
| `PUBLIC_ORIGIN` | `https://formday-fitplan-ccucle.onrender.com` |
| `TRUST_PROXY_HOPS` | 우선 0; 실제 경로 검증 후에만 조정 |

소스는 `../fitplan/core.js`와 정적 파일을 함께 사용하므로 빌드 컨텍스트에 `fitplan/`과 `fitplan-server/`가 모두 있어야 한다. 마이그레이션은 반복 실행할 수 있으며, 앱은 마이그레이션 실패를 무시하고 시작하지 않는다.

`render-internal` TLS 모드는 Render 환경과 내부 `dpg-…` 호스트에만 허용한다. Render 문서에 따른 내부 자체 서명 인증서를 수용하되 TLS 연결 자체를 요구한다. 일반 외부 DB 연결에는 인증서를 검증하는 `verify-full`이 기본이다. TLS가 실패해도 평문으로 재접속하지 않는다.

`TRUST_PROXY_HOPS=0`은 전달된 IP 헤더를 신뢰하지 않는다. 이 상태에서는 프록시 IP를 공유하는 이용자의 속도 제한이 함께 적용될 수 있다. 임의로 숫자를 높이지 말고 실제 Render 경로에서 헤더 위조가 제한되는지 확인한 뒤 올바른 hop 수를 설정한다.

### 2. 기존 주소에서 API 연결

우선 기존 정적 사이트에 `/api/*` → 새 계정 서비스의 `/api/*` **rewrite**를 추가해 브라우저의 출처를 유지하는 방식을 검증한다. 기존 브라우저 저장 기록이 같은 주소에 남는다는 장점이 있다.

Render 문서는 외부 URL rewrite와 요청 쿠키 전달을 설명하지만, 이 인증 구성에서 응답 `Set-Cookie`의 속성 유지와 사용자별 응답의 캐시 격리는 실제 배포로 확인해야 한다. 이를 검증하기 전 계정 기능이 운영 가능한 것으로 표시하지 않는다.

- API 응답의 `Cache-Control: no-store`와 프록시 응답의 동일한 정책을 확인한다.
- 가입/로그인 응답의 `__Host-FORMDAY_sid`가 현재 사이트에 저장되는지 확인한다.
- 새로고침 뒤 `/api/auth/session`과 `/api/state`에 쿠키가 전달되는지 확인한다.
- 다른 계정·쿠키 없는 브라우저가 앞선 응답을 캐시에서 받지 않는지 확인한다.
- 요청 본문, `Origin`, CSRF 헤더, 예상 사용자 ID가 전달되는지 확인한다.

이 조건을 만족하지 못하면 rewrite로 로그인 기능을 노출하지 않는다. 계정 서버가 정적 파일도 직접 제공하도록 준비되어 있으므로, 같은 출처의 웹 서비스 주소로 전환하고 `PUBLIC_ORIGIN`을 그 실제 주소로 바꾸는 방법을 제시한다. 이 경우 기존 브라우저에서 내보낸 백업을 가져오며, 다른 주소로 브라우저 저장소가 자동 이전된다고 설명하지 않는다.

공식 근거:

- Rewrite: https://render.com/docs/redirects-rewrites.md
- 정적 사이트 헤더: https://render.com/docs/static-site-headers.md
- 프록시 요청 전달 예: https://render.com/articles/how-to-proxy-analytics-through-your-own-domain

### 3. 활성화 전 실제 확인

1. 마이그레이션과 `/readyz`를 확인하고 내부 TLS 및 DB 접근 제한을 확인한다.
2. 임시 QA 계정 두 개와 분리된 브라우저 저장소를 사용해 가입·복구 코드·로그인·로그아웃을 확인한다.
3. 기존 비로그인 기록을 내보내고, 선택 전 자동 업로드가 없는지 확인한다.
4. 첫 기기에서 기기 기록을 명시적으로 옮기고 두 번째 기기에서 불러온다. 운동 세트·식단 영양값·체중·내 식품을 대조한다.
5. 두 기기의 수정 충돌, 네트워크 실패, 응답 유실 후 재시도, 세션 만료 후 재로그인을 확인한다.
6. 복구 코드로 비밀번호를 바꾸어 기존 세션이 더 이상 기록을 읽거나 쓰지 못하는지 확인한다.
7. iPhone/Safari에서 입력·복구 코드 복사·긴 모달·새로고침·쿠키 저장을 별도 확인한다.
8. 임시 계정과 QA 기록을 정리하고 실제 배포 커밋과 확인 결과를 남긴다.

자동 테스트에서 사용하는 PGlite는 SQL 스키마와 쿼리 동작을 검증하는 내장 PostgreSQL 환경이다. 실제 Render 서버의 TCP/TLS 연결, 다중 연결 잠금 경합, 백업 복구와 Safari 쿠키 정책 검증을 대신하지 않는다.

## 배포와 복원

검증한 계정 브랜치를 운영 브랜치에 반영한 뒤 정적 배포를 수동으로 갱신한다. 기존 v0.3 배포는 그 시점까지 유지한다. 자동 배포는 계속 끈다.

화면 코드 롤백은 서버 문서나 DB를 삭제하는 작업과 구분한다. 계정 활성화 후 v0.3 화면으로 돌아가면 기존 비로그인 저장소만 보이고 계정 캐시는 표시되지 않는다. 이를 계정 기록이 사라진 것으로 오해하지 않게 안내하고, 필요한 경우 계정 버전으로 다시 접속해 내보낸다. DB나 계정을 삭제해 롤백하지 않는다.

유료 DB의 제공 백업과 사용자의 JSON 내보내기는 복원 목적이 다르다. 서비스 전체 복원은 DB 백업으로, 사용자 선택 기록의 이동은 v3 JSON 백업으로 진행한다. 운영 전 실제 복원 절차도 확인한다.
